## 一句话定位

MCP Route Reliability Lab 是一个评测 Agent 工具路由是否应调用、澄清或拒绝的可复现实验项目，重点是让错误、数据来源和风险边界都可检查。

它是评测工具链，不是已经上线、能自主完成任务的 Agent 产品。

## 60 秒项目介绍模板

> “我关注 Agent 在多工具环境中调用错误工具的风险。这个项目不是再做一个聊天 Agent，而是构建可复现的评测流程：统一工具描述和查询标签，比较 BM25 与多语言嵌入路由，再用 Calibration 集估计正确率、选择风险策略，最后只对冻结的 Test 集评估一次。我的实际工作是【填写自己能展示的模块、代码或标注决策】。V1 AI 实验版有 40 个工具、300 条基础查询和 90 条变体；在包含 190 条记录的 Test 集上，两个基线 Top-1 分别是 0.1737 和 0.3211，5% 目标风险下都没有可用策略。我把这个结果保留下来，因为项目价值在于发现不可靠之处，而不是把实验包装成安全可部署。下一步是独立人工复核和更真实的任务数据。”

其中“190 条记录”指 100 条基础查询及其 90 条配对变体，**不是 190 个独立意图**。另有 112 条基础标签仍是生成器暂定结果；详见 [标注诊断](../../data/v1-ai-experimental/ANNOTATION_REPORT.md)。

## 架构怎么讲

1. **Tool Corpus 与查询：** 固定工具 schema、查询文本、标签和数据哈希；编号模板按意图族放入同一划分，减少可识别的跨集泄漏。
2. **路由：** BM25 或多语言嵌入模型只接收推理时查询与工具描述，输出排序候选；金标准标签不会传给路由器。
3. **校准与策略：** 只在 Calibration 集拟合置信度并选择阈值。没有满足约束的阈值时，策略标记为不可用，而不是发布一个看似安全的阈值。
4. **冻结 Test 与报告：** 配置冻结后评估 Test 一次，保存 Top-K、MRR、校准、风险—覆盖率、错误切片及绑定来源的清单。[演示流程](demo.md)

## 面试追问

**为什么要允许澄清或拒绝，而不是永远选一个工具？** 错误工具可能读取错误文件、误判 Git 状态或收到缺失参数。只给 Top-1 排名无法表达“目前不该调用”的情况，所以项目同时评测排序和弃权／澄清，并记录策略何时不可用。不能把“策略不可用”说成“风险已受控”。

**多语言 MiniLM 的 Top-1 只有 0.3211，原因是什么？** 先说明指标口径：Test 共 190 条记录，其中 Clarify 与 No-match 样本若被直接路由，会按严格口径算错。当前数据是合成且含配对变体，112 条基础标签仍是生成器暂定；这些都是解释结果时必须披露的限制。具体错误可从 [错误导出](../../reports/v1-ai-experimental/embedding/errors.csv) 检查，但没有消融实验就不要断言某一个因素是主要原因。例如 `v01_q_015` 要求“列出提交历史，不是查看单个补丁”，金标准是 `git.log`；模型把 `git.show` 排在第一、`git.log` 排在第二。

**为什么还不能叫稳定 V1.0？** 标注来自 AI，缺少独立人工复核；仍有 112 条生成器暂定标签，190 条 Test 记录也并非独立意图。更关键的是，两种基线的 5% 目标风险策略都不可用。现有报告只能支持“AI 实验版的测量结果”，不能支持生产安全保证。[Dataset Card](../../data/v1-ai-experimental/DATASET_CARD.md)

**你本人做了什么，AI 做了什么？** 如实给出【你亲自确定的需求、检查的标注、编写或修改的文件、执行的测试】和可以现场解释的证据。若使用 AI 辅助开发，就说明它帮助生成了哪些草稿或代码，以及你如何审查、验证和修正；不要把不熟悉的实现说成自己独立完成。
